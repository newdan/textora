# 关闭最后一个文件后的默认文档设计

## 背景

关闭最后一个文件后，`Workspace` 已正确移除原条目，但渲染入口会在工作区为空时提前返回。UI shell 因此没有刷新，sidebar 继续显示上一帧的文件状态。

产品预期不是允许零文档空态，而是始终保留一个可编辑的默认文档。这与应用启动时工作区为空便创建未命名文档的既有行为一致。

## 设计

由应用层统一维护“完成工作区导航操作后至少存在一个可编辑文档”的不变量。

`App::handle_workspace_effect` 收到会改变活动文档的工作区效果后，如果发现 `Workspace` 为空，则使用当前视口尺寸调用既有的 `Workspace::new_untitled`。随后沿用原有的活动文档变更流程，完成视口调整、display map 初始化、缓存清理、布局更新、重绘、标题更新和工作区持久化。

默认文档沿用现有 `new_untitled` 语义：内容为空、无文件路径、可编辑、初始为干净状态，并在 sidebar 中显示为未命名文档。

不在 `Workspace::close_entry` 内创建默认文档，因为 `Workspace` 不应承担应用级空态策略，也不应为关闭操作额外依赖窗口视口。也不在各个单项或批量关闭入口重复判断，以避免不同关闭路径行为漂移。

## 数据流

1. 用户关闭最后一个未固定文件，并完成可能的保存确认。
2. `Workspace::close_entry` 移除条目并返回 `NavEffect::ActiveChanged`。
3. `App::handle_workspace_effect` 检测到工作区为空，创建默认未命名文档。
4. 既有 `ActiveChanged` 处理初始化新文档并请求 reshape、layout、redraw、标题更新和持久化。
5. 下一帧向 tab bar 和 sidebar 注入包含默认文档的新列表，不再保留旧条目。

## 错误与边界

- 固定文件仍不可关闭，现有保护不变。
- 用户取消保存对话框时不关闭文件，也不创建默认文档。
- 关闭非最后一个文件时不创建额外文档。
- 批量关闭所有可关闭文件后同样只创建一个默认文档。
- 工作区数据结构仍允许在恢复和测试等内部阶段短暂为空；不变量只在应用处理完导航效果时恢复。

## 测试

- 将现有“关闭最后一个标签”回归测试改为断言工作区保留且激活一个默认文档。
- 断言默认文档为空、无文件路径、可编辑且不是脏状态。
- 运行该精确测试确认修复前失败、修复后通过。
- 运行 `textora-app` 库测试与编译检查，确认其他关闭和渲染路径不回归。
