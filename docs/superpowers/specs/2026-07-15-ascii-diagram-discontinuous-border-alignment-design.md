# ASCII 图断续边框累计对齐设计

## 背景

Markdown 代码块中的 ASCII 图按 Unicode 字素显示宽度构造字符网格。当前实现可以把单个右边框字符改画到更靠右的绝对列，但这个改动不会传递给同一行后续字符。因此前方边框被扩宽后，连接箭头、并排矩形和服务端外框仍停留在原始绝对列，产生新的重叠、阻断和锯齿。

`wps-focus-mvp-design.md` 的三个样例证明，服务端外框的位置必须从整行最左侧持续累计：客户端外框右边产生的对齐增量应传递给中间连接区和服务端；服务端左边产生的增量还应继续传递给服务端内容及右边。

## 目标

- 同一逻辑竖边允许部分行缺失或断开，能够归属的已有线段必须落在同一最终网格列。
- 同一逻辑横边允许缺口；已有横线仍位于各自行网格中心。
- 每行的最终横坐标从最左侧开始累计，前方边界的右移必须传递给后续所有单元格。
- 嵌套框、并排框、时间轴和连接箭头保持各自拓扑归属。
- 没有成对角点的开放时间轴也能形成独立竖向轨道，主干、竖线和箭头端点共线。
- 对齐通过插入虚拟空白列完成，不覆盖或穿过文字、箭头及其他图形字符。

## 非目标

- 不修改 Markdown 源文件。
- 不补画源图中完全不存在的边框段。
- 不左移已有内容。
- 不支持当前字符连接表之外的新箱线字符。
- 不对普通代码块启用 ASCII 图网格渲染。

## 核心模型

### 1. 拓扑归属与坐标计算分离

拓扑阶段只回答某个箱线字符属于哪个逻辑矩形的哪条边。归属证据包括：

- 上下角点定义的矩形行区间；
- 左右边的相对顺序和非交叉嵌套；
- 同一行内可形成的左右边对；
- 多行重复的边列或跨度模式；
- 同一字符只能归属一条逻辑边。

跨度只用于排除错误归属，不能用 `right - width` 反推服务端左边的最终坐标。不存在适用于所有图块的固定一列漂移上限。

上下横边也允许源列漂移。矩形候选从上到下使用开放栈匹配：下边只匹配水平区间正重叠的开放上边，优先最近开放行；同一最近行取最大重叠的唯一上边，最大重叠并列则保持歧义。每条上下边至多使用一次。

行内竖边数量与预期轨道数量相等时，按非交叉拓扑顺序作为高置信归属。数量不等的低置信行一次性联合“轨道历史列”与“矩形历史跨度”产生的全部候选；一般成员只有在完整候选集中 expected/actual 双向唯一、与任何候选均不交叉时才可归属。跨度证据的左右端必须同时满足条件并原子加入。候选删除后不重新唯一化，不枚举或最大化可能映射。

低置信行另有一个严格限定的边界拓扑不变量：首个预期轨道与首个实际竖边、末个预期轨道与末个实际竖边，在该位置同时得到轨道历史列直接支持，且不存在共享同一 expected 或 actual 位置的其他 direct 候选时，可以作为边界锚点。若锚点在完整候选集中恰好只有一个互相引用的跨度伙伴，才考虑原子恢复该矩形的另一侧；该伙伴还不得与任何“兼容全部已确认边界锚点”的候选交叉。与边界锚点共享 expected/actual 或交叉的候选已被边界拓扑事实否定，不参与伙伴冲突检查；其余候选不删除、不重新唯一化。伙伴为多个或仍与可行候选交叉时，只保留直接锚点，不选择伙伴。该规则不把 direct 证据普遍置于跨度证据之前，只利用有序边界不可能被更外侧成员越过这一拓扑事实。

### 2. 从左到右累计虚拟列

每个单元格保留源列，并记录由前方对齐产生的累计右移量：

```text
render_column(cell) = source_column(cell) + cumulative_shift_before_or_at(cell)
```

当某条边当前位于 `current_column`，轨道目标为 `target_column` 时：

```text
delta = target_column - current_column
```

若 `delta > 0`，在该边之前插入 `delta` 个虚拟列，并将该边及本行后续全部单元格右移 `delta`。这样移动客户端右边时，后面的箭头和服务端会整体继承增量，不需要让边框越过箭头。

右上角或右下角向右移动时，其左向横线连接需要延长 `delta`；只是继承前方累计偏移的后续箱线字符不得重复延长横线。因此累计位移与当前边产生的横线延长量必须分开存储。

### 3. 轨道按从左到右求解

同一图块内的逻辑竖边按最终视觉顺序处理。每条轨道的候选列必须使用已经包含前序累计偏移的 `render_column`，目标取已确认成员的最右当前列。应用本轨道增量后，再计算右侧轨道。

服务端外框的左边不能直接使用源列 `46–50` 或固定跨度推导。它必须先继承客户端及连接区产生的累计偏移，再形成服务端左轨道；服务端右轨道继续继承此前全部增量。

### 4. 缺口与歧义

- 行内没有可确认成员时，记录为 `Missing`，不创建字符，也不阻止其他行对齐。
- 多个拓扑方案等价时记录为 `Ambiguous`，不移动这些候选字符。
- 对于已经确认的边，右移通过插入虚拟列完成，后续内容整体移动，因此不再使用“目标路径必须全为空白”判断后续内容是否阻挡。
- 不能确认归属的字符保持其普通 ASCII 图字符语义；不得为了凑齐矩形强行认领内框或箭头端点。

### 5. 开放时间轴轨道

开放时间轴不依赖 `┌┐` 与 `└┘` 配对。检测阶段把一条连续横向主干中具有竖向连接的 `├`、`┼`、`┤` 视为有序锚点；只有当相邻行存在数量一致、顺序一致的 `│` 或终止箭头 `▼` 时，才建立独立的开放轨道组。

轨道成员按从左到右的拓扑顺序匹配，而不是要求源列相等，因为待修复输入的源列本身可能相差一列。每条开放轨道与矩形轨道一样，目标取已确认成员当前 `render_column` 的最大值，并通过行后缀累计右移完成吸附。`▼` 只作为终止成员参与归属和位移，仍沿用普通文字渲染，不转换成箱线几何。

若代码块仅包含开放时间轴而没有矩形角点，只要主干至少有两个竖向锚点、箱线字符达到既有阈值且至少一行提供对应竖向成员，也应进入 ASCII 图固定网格渲染。成员数量不一致或存在多种非交叉匹配时保持原始列，不做猜测。

## 数据依据

### 架构图 65–97

- 客户端外框左边稳定在源列 `0`，右边分布在 `36/37/38`。
- 服务端外框的源列会随前方内容变化；常见边对包含 `48→80`、`50→82`、`49→81`、`47→79`、`46→78`。
- 客户端右边先对齐后，服务端左边的当前列必须加上客户端产生的前缀增量。因此原始 `46–50` 和 `78–82` 仅是输入统计，不是最终目标列。
- 反馈箭头行存在缺边和额外竖线，要求拓扑阶段允许缺口且不能按最近距离认领。
- 反馈箭头行缺少客户端外框右边，但最右实际边仍由历史列直接支持服务端外框右轨道；该末端锚点与唯一互相引用的 `46→78` 跨度伙伴共同确认服务端外框，最终累计到 `51→84`。

### 滚动窗口 116–139

- 下方矩形左边稳定在 `1`，右边分布在 `58/59/60/61`。
- 角点跨度为 `58`，内容行最大跨度为 `60`，偏差达到两列，证明固定一列上限不成立。
- 上方时间轴没有成对矩形角点，必须形成独立开放轨道，不能被并入下方矩形轨道。
- 主干源列为 `[2, 19, 36, 46, 56]`，内容与箭头源列为 `[2, 20, 37, 47, 57]`；累计右移后的共同目标为 `[2, 20, 37, 47, 57]`。

### 环形缓冲区 220–233

- 左边稳定在 `0`，右边分布在 `59/60`。
- 该独立矩形应通过同一累计模型对齐，不能增加真实样例专用分支。

## 数据流

```text
代码块文本
  → Unicode 字素与源显示列
  → 角点矩形及嵌套关系
  → 全图块逻辑边归属（允许 Missing / Ambiguous）
  → 逻辑轨道按从左到右排序
  → 基于当前 render_column 推导轨道目标
  → 在成员边处插入虚拟列并传播到行后缀
  → 渲染累计列及局部横线延长
```

## 测试

1. 最小并排矩形：左侧右边右移后，右侧矩形所有单元格继承增量。
2. 同一行连续执行两个轨道对齐：第二轨道必须使用第一轨道传播后的当前列。
3. 右角点的局部横线延长只发生一次；继承前缀偏移的后续横线不得重复延长。
4. 完整架构图：全部 31 行走最终 `DrawList`；已有客户端边、服务端左边和服务端右边分别使用累计后的像素列，反馈箭头保持在客户端与服务端之间。
5. 滚动窗口允许两列跨度变化；最终 `DrawList` 的 11 行外框（含底边角点）左右边分别共线。
6. 环形缓冲区最终像素右边共线。
7. 直接边界锚点存在同轴 direct 竞争时不得成立；只有一个互相引用伙伴且该伙伴不与仍可行候选交叉时才可恢复成对边。
8. 嵌套缺边、歧义边和并排框既有回归继续通过。
9. 单独的开放时间轴无需矩形角点即可被识别；主干、内容竖线和 `▼` 最终落在相同的五个像素列。
10. 开放轨道成员数量不一致或归属有歧义时保持源列，不移动无关箱线字符。
