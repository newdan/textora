# ASCII 图树形分支干扰外框对齐修改方案

**日期：** 2026-07-16
**状态：** 已实施（提交 `07a26d6d`、`74824085`）

## 1. 背景

Markdown fenced code block 会在满足 ASCII 框线图识别条件时进入固定网格渲染。布局阶段先按 Unicode 字素计算源显示列，再识别矩形和开放时间轴的逻辑竖轨，最后把同一轨道的成员右移到共同的 `render_column`。渲染阶段只消费该结果，将 `render_column × cell_width` 转换为像素坐标。

下面这类图表仍会出现外框右边界错位：

```text
Electron (UI Shell)          Go (Agent Core)
┌──────────────────────┐    ┌─────────────────────────────┐
│  Main Process         │    │  WebSocket Server            │
│  ├─ spawn Go 二进制    │◄──►│  ├─ token 认证               │
│  └─ BrowserWindow     │ WS │  └─ 收发 JSON 消息           │
│                       │    │                              │
│  Renderer (Chat UI)   │    │  Agent Loop                  │
│  ├─ 流式对话           │    │  ├─ Orchestrator (主 agent)  │
│  ├─ 工具调用卡片        │    │  └─ Worker (子 agent)       │
│  ├─ 子 agent 进度      │    │                              │
│  └─ 任务面板            │    │  LLM Provider               │
└──────────────────────┘    │  ├─ Anthropic (流式 SSE)      │
                            │  └─ OpenAI 兼容               │
                            │                               │
                            │  工具系统 (8 tools)            │
                            │  条件式 Prompt 构建            │
                            │  Skills 系统                  │
                            │  会话持久化                    │
                            └─────────────────────────────┘
```

问题只发生在非活动代码块的固定网格预览路径。编辑态仍按普通文本渲染，不属于本次修改范围。

## 2. 已确认根因

### 2.1 复现数据

左侧外框右边界的源列和最终渲染列如下：

| 内容行 | 源列 | 当前渲染列 | 是否被认领为左框右轨成员 |
| --- | ---: | ---: | --- |
| 顶边 `┐` | 23 | 26 | 是 |
| `Main Process` | 24 | 26 | 是 |
| `├─ spawn Go 二进制` | 25 | 25 | 否 |
| `└─ BrowserWindow` | 24 | 26 | 是 |
| 空行 | 24 | 26 | 是 |
| `Renderer` | 24 | 26 | 是 |
| `├─ 流式对话` | 25 | 25 | 否 |
| `├─ 工具调用卡片` | 26 | 26 | 是 |
| `├─ 子 agent 进度` | 25 | 25 | 否 |
| `└─ 任务面板` | 26 | 26 | 是 |
| 底边 `┘` | 23 | 26 | 是 |

因此最终存在第 25、26 两个像素轨道。截图中的三段凹陷竖线正是未被认领的第 25 列成员。

### 2.2 数据流断点

1. `├` 的连接属性包含 `up + down`，所以 `is_vertical_edge()` 会把树形列表分支和矩形竖边一并加入实际竖边候选。
2. 当前图表同时存在左右两个矩形。位于两个矩形共同有效区间内的行预期具有四条矩形竖轨。
3. 没有树形分支的行恰好包含四个实际候选，进入高置信路径并按从左到右的拓扑顺序直接归属。
4. 含 `├` 的行多出一个或多个候选，进入低置信路径。
5. 低置信路径当前只使用“轨道历史源列”和“矩形内部历史跨度”生成候选。第 25 列不等于左框右轨已支持的 `{23, 24, 26}`，`0 → 25` 也不等于已支持的矩形跨度 `{23, 24, 26}`，所以该边不会成为候选。
6. 后续对齐只移动已经归属轨道的成员。未归属的第 25 列边保持源列，渲染器再忠实地将其绘制到错误的 x 坐标。

根因位于 `crates/markdown/src/layout/ascii_diagram.rs` 的低置信轨道归属阶段，不在 Unicode 宽度、字体 shaping 或 `crates/markdown/src/render.rs` 的像素绘制阶段。

## 3. 修改目标

- 在“并排矩形 + 内部树形分支 + 外框源列漂移”的组合中，唯一识别可证明的矩形外框成员。
- 本例左框右边、右框左边和右框右边分别继续对齐到各自最终轨道。
- 树形 `├`、`└` 保持普通框线字符语义，不被误认成矩形外框。
- 保留既有缺边、嵌套矩形、并排矩形、开放时间轴和反馈箭头的歧义保护。
- 不通过最近距离、固定漂移阈值或样例专用列号推断边界。
- 不修改 Markdown 源文本、公开布局 API、编辑态回退路径或渲染器。

## 4. 非目标

- 不重新设计完整的 ASCII 图语法或建立通用图解析器。
- 不识别树形列表的父子关系。
- 不补画源文本中不存在的边框。
- 不左移任何现有字符。
- 不为 `├`、`└` 增加全局过滤规则。
- 不改变开放时间轴的主干和终止箭头归属算法。

## 5. 方案比较

### 方案 A：增加相邻逻辑轨道距离证据（采用）

高置信行除了记录单轨源列和同一矩形左右边跨度，还记录按最终拓扑顺序排列的相邻逻辑轨道之间的源列距离。低置信行可用这些距离生成相邻轨道的原子候选对。

本例中，左框右轨到右框左轨的历史间距稳定为 5 列。失败行存在唯一符合该证据且拓扑顺序正确的 `25 → 30` 组合，因此可以把第 25 列认领为左框右轨，同时排除第 3 列的树形 `├`。

优点：

- 使用已有多行结构事实，不依赖字符内容或固定误差范围。
- 能覆盖矩形外框自身宽度变化但矩形间连接区保持稳定的图表。
- 可沿用现有候选完整集、双向唯一、非交叉和原子伙伴验证框架。

代价：

- 需要新增一种证据类型，并明确相邻轨道身份，不能只保存无归属的距离集合。
- 需要防止单侧距离命中绕过矩形内部成对约束。

### 方案 B：识别并过滤树形分支

根据 `├` 或 `└` 右侧是否紧跟 `─` 和文字，把它们排除出矩形竖边候选。

不采用原因：

- 表格分隔线、带标题框线和开放时间轴也可能使用相同局部形态。
- 局部字符模式不能证明该字符不属于矩形或开放轨道。
- 会把当前的拓扑归属问题转化为不断扩张的字符启发式规则。

### 方案 C：按最近列或允许一列误差吸附

让第 25 列匹配历史目标第 26 列。

不采用原因：

- 已有真实样例证明漂移可能超过一列。
- 嵌套框、缺边行和连接箭头中可能同时出现多个距离相同的候选。
- 最近距离不能证明逻辑归属，容易破坏已有安全降级行为。

## 6. 推荐设计

### 6.1 新增相邻轨道间距证据

在 `vertical_border_tracks()` 的高置信扫描期间，已有代码已经得到：

- 当前行的 `expected_track_indices`；
- 与其按拓扑顺序一一对应的 `cell_indices`；
- 每条轨道的 `supported_columns`；
- 每个矩形的 `supported_spans`。

新增按轨道身份索引的相邻距离集合：

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq, PartialOrd, Ord)]
struct AdjacentTrackPair {
    left_track_index: usize,
    right_track_index: usize,
}

type SupportedAdjacentGaps = BTreeMap<AdjacentTrackPair, BTreeSet<usize>>;
```

每个高置信行按 `expected_track_indices.windows(2)` 遍历相邻轨道，同时读取对应的实际单元格列：

```text
gap = right_source_column - left_source_column
```

仅记录严格递增的相邻列。键必须包含左右轨道身份，禁止把图中任意两条轨道的距离混入同一个全局集合。

### 6.2 生成原子相邻候选对

低置信行构造完整候选集时，增加 `add_adjacent_gap_supported_candidates()`：

1. 遍历本行预期轨道序列中的每对相邻轨道。
2. 读取该有向轨道对的历史距离集合。
3. 遍历实际竖边候选中保持从左到右顺序的两个位置。
4. 当实际列差命中该轨道对的历史距离时，为两端记录互相引用的原子伙伴关系。

相邻距离证据不能退化成两个独立的单边候选。只有左右端同时存续、互相引用并满足现有非交叉约束时，才能共同归属。

### 6.3 与现有跨度证据分离

矩形内部跨度和相邻轨道距离表达不同事实：

- `supported_spans[rectangle_index]`：同一个矩形的左边到右边；
- `supported_adjacent_gaps[(left_track, right_track)]`：最终拓扑序列中任意相邻轨道之间的距离，可能跨越两个矩形之间的连接区。

两种证据不得合并成无类型的距离集合。候选证据应明确伙伴来源，避免把一个矩形的宽度错误复用为另一个轨道对的间距。

推荐将现有 `span_partners` 泛化为仍然保持原子关系的伙伴集合，命名为 `atomic_partners`：

```rust
#[derive(Clone, Debug, Default, PartialEq, Eq)]
struct AssignmentEvidence {
    directly_supported: bool,
    atomic_partners: BTreeSet<CandidatePosition>,
}
```

矩形跨度和相邻轨道距离都通过同一个原子伙伴登记函数写入，但候选生成函数分别保留，以维持职责和测试边界。

### 6.4 保留完整候选集否决规则

新增证据必须继续遵守现有低置信约束：

- 在完整候选集中评估 expected/actual 双向唯一性；
- 候选删除后不重新唯一化；
- 任何候选与仍可行候选交叉时不得强制归属；
- 一个实际字符只能归属一条逻辑轨道；
- 原子伙伴必须成对存在，不能只采纳其中一端；
- 多个同等相邻间距组合存在时保持歧义，不选最近或最左组合；
- 既有直接边界锚点只能恢复唯一、互相引用且不与仍可行候选冲突的伙伴。

相邻距离只增加可证明候选，不提升某类证据的全局优先级。

### 6.5 对齐和渲染保持不变

一旦第 25 列边被加入左框右轨，现有 `align_vertical_tracks()` 会把该轨道目标计算为第 26 列，并通过 `align_row_suffix_to()` 将该边及行后续内容整体右移一列。

这会自然传播到中间箭头和右侧矩形，无需修改 `render_ascii_diagram_row()`。右移量仍由 `render_column_shift` 表达，局部横线延长仍由 `left_extension_columns` 表达。

## 7. 数据流

```text
Unicode 字素与源列
  → 矩形候选及逻辑轨道顺序
  → 高置信行归属
  → 记录单轨历史列
  → 记录矩形内部跨度
  → 记录有身份的相邻轨道距离
  → 低置信行构造完整候选集
  → direct / 矩形跨度 / 相邻距离联合产生证据
  → 双向唯一、原子伙伴、非交叉与边界锚点验证
  → 已确认成员进入轨道
  → 从左到右累计对齐
  → 现有固定网格渲染
```

## 9. TDD 实施顺序

### 阶段一：锁定真实回归

1. 在 `ascii_diagram.rs` 加入完整原始图表测试。
2. 收集左侧外框每一行真实右边界的 `render_column`。
3. 断言所有列相同，并运行单测确认 RED：当前实际集合为 `{25, 26}`。
4. 在 `render.rs` 加入最终像素 x 回归并确认 RED。

### 阶段二：增加相邻轨道证据

1. 增加 `AdjacentTrackPair` 和 `SupportedAdjacentGaps`。
2. 为高置信行记录相邻轨道距离。
3. 写最小测试证明距离按轨道身份隔离。
4. 增加相邻距离原子候选生成逻辑。
5. 运行真实布局回归，确认左框右边界全部为第 26 列。

### 阶段三：强化歧义保护

1. 加入两个相同距离组合均可成立的低置信行，断言保持源列。
2. 加入数值距离相同但轨道身份不同的夹具，断言不得复用证据。
3. 运行既有缺边、嵌套框、并排框、开放时间轴、反馈箭头和边界锚点测试。

### 阶段四：最终像素验证

1. 运行完整图表 `DrawList` 测试。
2. 断言左框所有已有右边界共享一个 x。
3. 断言右框左、右边界分别共享各自 x。
4. 断言连接箭头保持在左框右边和右框左边之间。

## 10. 验收标准

- 原始 Electron/Go 图表的左框右边界所有已有线段共用第 26 渲染列和同一像素 x。
- `spawn Go 二进制`、`流式对话`、`子 agent 进度` 三行不再形成第 25 列凹陷。
- 树形分支字符不被移动到外框轨道。
- 右侧 Go 外框的左右边界仍各自共线。
- `◄──►` 连接箭头和 `WS` 标签保持在两框之间，不与边界重叠。
- 多解或证据不足的低置信行继续保持源列。
- 现有 50 项 `layout::ascii_diagram::tests` 全部通过。
- `textora-markdown` 全量测试、格式检查、编译检查及项目验证脚本全部通过。

## 12. 风险与回滚边界

主要风险是相邻距离证据扩大低置信候选集合，使以前保持未归属的字符获得新伙伴。通过以下约束控制：

- 距离证据绑定确切的有向轨道对；
- 两端必须原子加入；
- 完整候选集仍参与唯一性和交叉否决；
- 多解保持歧义；
- 不增加固定距离容差。

实现应保持在 `ascii_diagram.rs` 的证据收集和候选构造范围内。如果需要修改渲染器、字符宽度计算或增加样例专用分支，说明当前方案没有命中根因，应回滚该方向并重新分析。

## 13. 实施补充：树形分支行的候选范围

相邻间距证据只在当前行含树形 T 形分支 `├` 或 `┤` 时生成；普通只含竖边和角点的框图保持原有跨度候选行为。树形分支行中，若跨度候选端点与直接支持冲突、其两个预期位置相邻，并且它实际交叉一条唯一且直接兼容的相邻间距候选对，才跳过该跨度候选。

这只移除会阻断已证明树形分支行相邻链的跨度候选；不改变通用唯一性、非交叉或边界锚点判定，也不让普通框图获得新的相邻间距候选。
