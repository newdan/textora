# 编辑边界验证与修复

## 分阶段实施

1. 保存：统一字节序列化，CRLF 不重复 CR，混合换行与 BOM 保留；覆盖重复保存与重开。
2. 原子块：统一空段映射，先删可编辑空段，再保护分割线与代码围栏；代码正文使用字面删除；闭围栏按容器路径识别。
3. 段落拆分：持续编辑实例保存拆分来源，补充选区、Unicode、连续编辑及历史测试。
4. 原生验收：扩展 LF/CRLF、Shift+Enter、粘贴与多块样本；新构建独立 bundle，检查截图和实际保存结果。
5. 全项目验证，记录环境不可执行项及未解决失败，不把阻断算通过。

## 段落拆分来源协议

`ab` 从中间拆分和 `a\nb` 在第二行起点拆分可能得到同样的 `a\n\nb`。仅凭当前源码无法决定退格应该恢复 `ab` 还是 `a\nb`。因此冷启动的无状态测试不足以验证该可逆操作。

由 Markdown 编辑实例记录单次拆分的逆替换、光标和实际插入片段。生成计划不代表提交；只有后续源码更新精确等于计划产物才确认记录。未提交或被替换的计划不得生效。与拆分边界不重叠的编辑变换记录偏移，修改边界则失效；退格仅在对应光标及插入片段仍匹配时使用逆替换。撤销/重载等外部更新通过同一源码同步入口校验，不依赖应用状态或 UI 跨层访问。

测试使用同一 view、递增 generation，覆盖直接回退、输入删空后回退、未提交计划、边界修改失效、多次拆分以及 Undo/Redo 与源码同步。

## 原生验收新增：文件监听阻塞

批量保存关闭测试夹具时，主线程采样停在 `refresh_file_monitor_roots → replace_roots → recv`；后台停在 macOS FSEvents 注册。现有实现每次导航先撤销再注册全部根目录，放大系统监听延迟。

按顺序拆分为三个子任务：

1. 监听器协议和回归：先以可控阻塞后端复现同步等待、重复订阅和失败状态不一致；改为后台初始化、异步目录请求、差量订阅，连续请求合并到最新目录集合。关闭不等待可能阻塞的系统调用，后台只持有自己的通道和订阅。
2. 应用接入：监听完成、路径变化、错误采用类型化结果；新订阅完成触发一次文件安全检查，覆盖注册期间的事件空隙。错误可见，不静默吞掉。
3. 重建与验收：旧构建的 41/110 原生结果保留为历史；新构建重新记录证据。每项完成保存重开后关闭其夹具页签，避免测试长期累积订阅；再执行全项目验证。

订阅差量通过 `Watcher::paths_mut` 单批提交，避免 macOS 每个目录单独启停流。即使某一路径失败，也提交此前成功的变更以恢复保留订阅；无差量时不创建批次。后端初始化、请求和退出的阻塞回归使用可控门闩，发布失败和完成事件均需唤醒 UI。

## 工作区恢复的同类阻塞

清理旧 textora 验收进程后，提升权限环境的 `session_workspace_identity_mismatch_closes_the_unexpected_workspace` 仍在原有两秒断言失败。`notora-core::WorkspaceFileMonitor::start` 同步等待后台 FSEvents 注册，阻止工作区后台准备返回。此前仅记录环境差异不足以解决生产阻塞。

按三个子任务处理：

1. 在 `notora-core/src/file_monitor.rs` 提取可注入后端构造（保持原同步语义），用门闩复现启动等待；随后改为异步启动、非阻塞关闭。结果协议包含订阅完成、文件批次和错误。
2. 工作区索引器接入结果协议：订阅完成补全量扫描，失败向产品事件报告；监听失效后保留用户命令处理，不能因事件通道断开停止索引工作线程。变更控制在监听器、core 导出和 controller 三个源文件。
3. 复测原三项恢复失败、整个工作区测试及 verify.sh。此模块不属于当前冻结 textora 二进制，不继承或改变其原生截图证据。

## 连续保存的冲突误报

鼠标专项在插删、跨块替换及历史操作间反复保存，生成了与当前磁盘正文完全相同的冲突副本。`FileSafetyMonitor::observe` 只比较旧磁盘 revision；异步 dirty 快照排队期间本地保存已经完成，revision 改变就被当作外部冲突。

先新增两个失败回归，分别覆盖已跟踪文件和恢复时的 dirty 快照。磁盘内容与快照字节完全相同时，更新监听基线并返回 Unchanged；只有两份内容有分歧才创建冲突副本。回归包含 LF、CRLF、BOM，以及接着发生真正外部改动仍创建冲突副本的检查。14 项文件安全回归通过后，重建独立 `editing-self-save-audit` 构建；此前 `editing-monitor-audit` 的 33 项矩阵和专项诊断保留，不迁移通过数。

文档级补充回归进一步复现：直接比较缓冲区文本时，BOM 与 CRLF 序列化仍会造成内容不等。runtime 的文件安全候选改为复用 `document_save_snapshot`，与实际保存保持完全相同的字节表示，不另写 BOM 或换行归一化。该测试通过真实后台 worker 检查结果及目录中没有冲突副本。第一轮 self-save 构建和验证发生在此调整之前，保留为诊断；最终构建须在代码稳定后重新冻结并整次验证。

## 长代码行末的横向可见性

独立原生夹具的源码定位到 `VISIBLE_END` 后，在 Markdown 模式插入 `[END]` 并保存，实际字节位置准确，但文字和光标均在窗口右侧之外。回归测试进一步记录到 36 个不可见光标，覆盖两种换行、普通／引用／列表代码块以及宽窄视口往返。代码布局为整行塑形，绘制被代码框裁剪，却没有让横向视口跟随光标。

按顺序分为三个子任务，每个子任务控制修改范围：

1. 复现与行几何：让活动代码块整体横向移动，保留逻辑行、源码投影与代码字体塑形，复用光标的字素 advance 计算；验证导航和缩放后光标可见、鼠标命中仍返回相同源码字节。非活动 ASCII 图预览保持原布局。
2. 裁剪与高亮：先复现长行选区／搜索高亮溢出，再根据代码块的可视边界裁剪，兼顾容器缩进和滚动偏移；不将光标简单钳制到边缘。
3. 冻结与验收：`editing-complete-audit` 构建在此修复之前，完整验证以 143 主动终止，证据仅保留为历史。修复稳定后创建新运行，先完成原生专项，再执行固定矩阵和全部项目验证，不继承旧构建的通过数。

### 横向视口设计复审

仅按当前位置计算最小横移量，虽可使光标可见，却可能让每次 Left 都重新贴到右边界。这说明横向视口不能作为无状态布局公式，必须保存编辑实例的视口偏移。新增连续 Left 的失败复现后，撤回块布局中的静态横移，改由 LazyLayout 在发布平面行映射前统一维护代码视口：光标仍在可视区时保持偏移，仅越过边界或尺寸／文本收缩时调整。行矩形、绘制、点击与高亮继续共享这次变换；重建布局时继承视口状态，源码锚点变化后重新定位。

该复审按顺序拆分为：失败回归与旧方案撤回；布局状态和统一发布；编辑引擎重建接入、回归及重新冻结。每阶段不超过三个修改文件。`editing-viewport-audit` 的完整检查在新增测试的 single-range-in-vec-init Clippy 错误处退出 101，未进入全项目测试；该轮不算完整通过，也不继承到下一构建。

源码更新后还会先走 `prepare_current_source_layout` 查询布局入口。该入口曾绕过视口继承，单修渲染重建不足以保持插入位置。现由统一的 `create_layout_with_view_state` 初始化两个入口，继承源码代次、选区、编辑上下文与代码视口；估算阶段不覆写精排视口。连续 Left、插入及重新点击的回归均通过。

长代码行末的 IME 组合另有失败复现：240px 视口内组合光标绘于 x≈253。代码原本在布局后叠画组合文字，现让代码块的无选区组合复用已有组合预览布局，下划线通过代码框统一裁剪。补充普通／引用／列表、LF／CRLF、中文、长组合、组合字符及 emoji，检查绘制光标、候选锚点、原字节和取消后几何。最新 32 组边界测试、1446 项 Markdown 库测试和工作区 Clippy 全部通过；尚需新的 `editing-code-viewport-audit` 冻结构建、完整 verify.sh 与真实窗口验收。

专项定位中以 SHA-256 证明复制前后的测试二进制相同，再放入独立临时目录执行，避开 macOS CFBundle 对庞大 deps 目录的反复扫描。原 Cargo 尝试及采样保留，最终完整验证仍按原始脚本执行，不把临时目录诊断视为完整项目通过。

## 长文档屏外光标与保存队列复审（2026-10-15）

`editing-code-viewport-audit` 的冻结构建在原生专项中发现：源码模式已到第80组代码末尾，切回 Markdown 后仍显示第1段；Markdown 的 Cmd+Down 和屏外输入同样只更新源码位置，未显示编辑位置。真实保存字节与插入标记排除了焦点或重放错误。应用级真实 Markdown 渲染回归分别复现文档首尾跳转、选区延伸、屏外输入及模式切换。常规路径补齐同步源码后的最小滚动；另以尚未产生首帧的模式切换复现几何尚不可查询的情况，采用纯数据 `RevealCursor(byte)` 请求，待布局和精排发布后处理。请求只执行一次，手动滚动可以取消，不能在每帧将视口拉回光标。

按顺序拆为三个子任务：应用导航／编辑回归与入口收口（app_tests、dispatch/editor、dispatch/wysiwyg）；延迟显示协议与布局实现（ui/plugin、markdown/view、view_navigation）；首帧、手动滚动和真实窗口重新验收。每个子任务控制在三个文件以内。

系统输入法探针中再次出现自身保存冲突，先前仅比较序列化内容的修复不足以覆盖“保存后继续编辑”。重新审查发现 SaveSession 和 FileSafetyWorker 在独立线程执行，本地保存的磁盘基线未按顺序交给监控。新增失败测试覆盖监控未建立／已建立、UI 尚未接收／已接收保存完成的四种组合。修复将启用文件监控的 runtime 的保存也送入同一 I/O 队列，成功写入后先确认磁盘版本，再处理观察；已确认的本地版本链允许连续保存快照衔接，新的外部基线不能被旧本地版本替换。UI 确认保存完成后回传 AcknowledgeSave，裁去不再需要的前驱版本，不依赖轮询时长或内容相等来掩盖竞态。

该修复按顺序拆为：复现与文件队列协议／实现（file_safety、document_save、file_safety_session）；runtime 接线与完成确认（editor_runtime/mod）；竞态、连续保存、门闩控制的真实并发顺序及外部修改保护回归。已有直接保存 API 和未启动文件监控的产品路径保持原协议。

还以独立失败测试确认：真实外部冲突产生的副本绑定到页签时丢失了磁盘基线，因此继续编辑后保存会错误拒绝。冲突结果现在携带副本自身的 DiskRevision，应用据此绑定；测试同时确认原外部文件不变、冲突副本后续再次被外部修改时仍拒绝覆盖。该子任务仅涉及 file_safety 与 app_lifecycle。
