# Textora 与 Notora 原生窗口走查

**2026-11-20，macOS 27.0.1（26A434）。** 两端的编辑器焦点、点击定位、获得编辑焦点后的拖选、已保存窗口的关闭均有实测证据。真实拼音输入法提交两端均未验证；Notora 从文件卡片直接起拖的首次尝试有异常，单独保留记录。未修改业务代码。

## 隔离和验收方法

- 在含本轮重构的工作树用 `cargo build --locked -p textora-app -p notora-app` 构建。为两端各建独立的临时 macOS 应用包和 Bundle ID，不使用正在运行的正式 Notora。启动器只为这两个进程覆盖 `HOME`（Textora 使用临时 `.edit+`）和 `NOTORA_CONFIG_DIRECTORY`（Notora 会话及缓存写入临时目录）。
- 本轮目录是 `/private/tmp/textora-native-walkthrough.nRpAf8`。两个不同文件名的 UTF-8 纯文本夹具，初始字节均为 `abcdefghij\nklmnopqrst\nuvwxyz\n`。通过原生窗口截图观察编辑区，点击或拖选后以退格精确探测范围，再用 `⌘S` 保存，最后用 `cmp` 断言字节。关闭后再次核对。临时目录不是长期归档。

## 待补与复测

- 系统输入菜单未能通过自动化访问，发送的组合键没有建立可确认的中文输入法会话。不要用粘贴中文替代。复测时先在系统菜单栏选中已启用的中文拼音输入源；分别打开两个隔离包，单击第三行行首，输入 `ni`，捕获预编辑和候选，显式选「你」，保存，再用 `cmp` 确认第三行变成 `你uvwxyz`，保留各自的行尾。还要确认没有落盘的原始字母 `ni`。
- 若要判定 Notora 从卡片直接起拖是否存在问题，用带末尾 LF 的新夹具，把「点击文件卡片 → 直接拖选第一行 → 退格」与「先单击编辑区 → 拖选同一范围 → 退格」分别执行并独立检查保存字节。不要据本次单次观察定性。
- 本轮没有覆盖脏窗口确认、系统输入源切换后的焦点恢复、Markdown 或思维导图视图，也不替代完整原生编辑验收。

## 非 IME 原生复测结果

之后成功绑定了上述两个隔离窗口。所有修改都发生在临时纯文本夹具。关闭前用 `cmp` 确认两份磁盘文件尚未包含未保存的编辑；关闭后只查运行清单，不再查询被关闭的窗口，以免工具重启应用。两个隔离进程均退出，正式 Notora 仍在运行。

| 项目 | Textora | Notora |
| --- | --- | --- |
| 跨应用切回后继续编辑 | 切回后未再点击正文，按回车成功在文件末尾新增空行。原来的行内插入位置未保留，本次未隔离窗口激活方式的影响。 | 切回后未再点击正文，光标仍在第二行行首；右移一位再退格，只删掉了 `l`。 |
| 关闭有未保存修改的窗口 | 点原生关闭按钮后退出。源文件精确变为 `abxcdefghij\nklmnopqrst\nuvwxyz\n\n`，含最后一次未显式保存的修改。 | 点原生关闭按钮后退出。源文件仍为 `abcdij\nklmnopqrst\nuvwxyz\n`；隔离目录生成一份 `.dirty` 快照，解码后精确等于 `abcdij\nmnopqrst\nuvwxyz\n`。只验证了快照内容，未操作恢复界面。 |

**Notora 从卡片直接起拖的异常复现。** 点击已选文件卡片后，不先单击正文，直接从第一行 `e` 前拖到 `i` 前。截图没有目标选区，随后退格和保存删掉第二行的 `o` 而不是 `efgh`，末尾 LF 保留。撤销、保存恢复基线，先单击正文，再用同一窗口的同一组坐标拖选；截图出现选区，退格和保存只删掉 `efgh`。两轮未命中时删除的位置不同，不能把位置差异当作根因。无窗口测试仍通过；下一步应记录原生按下／拖动坐标、焦点及捕获变化再定位。本轮不修业务行为，也不验收 IME。

## Notora 原生拖选事件追踪

在新的隔离包和同内容夹具上，临时观测 winit 窗口事件、产品路由和纯文本命中。诊断包和日志位于 `/private/tmp/notora-native-pointer-trace.FESGl0`；临时日志代码在启动诊断包前从工作树撤除。未输入或保存正文。

| 检查项 | 失败序列中实际收到的事件 |
| --- | --- |
| 原生焦点 | 窗口启动时收到 `Focused(true)`，但到正文按下前已经收到 `Focused(false)`；拖选过程中没有恢复。重启对照也在卡片释放之后、正文按下之前失焦。 |
| 坐标与路由 | 正文按下 `(1245, 173)`、移动和释放 `(1304, 173)` 均与请求一致；窗口和产品层均未消费正文按下。 |
| 双层焦点 | 正文按下把产品焦点从 `CardList` 切到 `Editor`，无模态阻挡，但编辑器输入上下文仍是 `Inactive`。这与 [Notora 的窗口与产品焦点合取](../crates/notora-app/src/events.rs) 一致。 |
| 捕获与命中 | 捕获一直为 `None`，编辑器没有执行正文命中，光标和选区保持原值。失焦状态下先单击正文，再用同样的坐标拖，也被同一门槛拒绝。 |

这解释了带日志的失败：**收到正确坐标不等于原生窗口已激活**。结果还不能说明为何桌面窗口失焦，也不能据此认定上一轮每次失败的原因。不要放宽编辑器的失焦保护；需要在日志确认窗口持续获焦时，用真实鼠标复核从卡片直接起拖。

### 2026-11-22：获焦对照

- 重启隔离实例后，日志记录了一次原生获焦时的按下：坐标约为 `(3056, 753)`，在正文空白处。编辑器确实建立并释放了 `TextSelection` 捕获，但这不是目标拖选。随后在目标坐标的自动化重放发生于 `Focused(false)` 之后，仍未建立捕获。两者不能合并成一次前台成功。
- 将[无窗口测试](../crates/notora-app/src/runtime/tests.rs)改为配对对照：从相同的卡片列表焦点发出相同的按下、移动、释放序列，只切换窗口焦点。失焦时产品焦点虽转到编辑器，光标和选区不变，也不建立捕获；获焦时建立捕获，释放后选区精确为字节范围 `4..8`。
