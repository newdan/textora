# Notora 笔记加密设计

日期：2026-08-03

状态：待安全评审

关联规范：[`2026-08-03-notora-editor-area-design.md`](./2026-08-03-notora-editor-area-design.md)

## 1. 范围与非目标

本文档定义 Notora 加密笔记的威胁边界、文件协议和生命周期，作为单独加密引擎计划的输入。编辑区计划在本设计通过安全评审并完成引擎验收前，只能创建和保存普通笔记；不得通过 catalog 字段或 UI 文案宣称文件已加密。

加密保护工作区笔记正文及其敏感元数据，不保护操作系统、编辑器进程或用户主动导出的明文。密钥丢失时不提供绕过恢复；恢复只能依靠用户保存的密钥备份。

## 2. 威胁边界

攻击者假设可以读取工作区目录、catalog、FTS 数据库、临时文件、冲突副本和备份文件，但不能在应用运行期间注入代码或读取受操作系统保护的密钥存储。应用崩溃、断电、外部修改和半写入文件均属于需要处理的正常故障。

必须防止：

- 从文件名、路径、文件头、catalog、FTS、dirty snapshot、冲突副本或崩溃恢复文件推断正文、标题、标签和摘要；
- 通过篡改版本头、nonce、密文或认证标签使应用接受损坏或篡改内容；
- 保存失败时用空文件、明文文件或错误 catalog 状态覆盖仍可恢复的旧密文；
- 解锁后把明文写入普通 autosave、日志、诊断信息或临时导出路径。

不承诺防护：已解锁期间运行在同一用户权限下的恶意进程、用户截屏、用户复制明文，或操作系统已经失陷的场景。

## 3. 加密文件协议

使用经过审计的成熟密码库提供 AEAD，不自行实现密码学原语。首个实现必须在评审中明确库与版本，并锁定依赖哈希。推荐采用 XChaCha20-Poly1305 或同等级的现代 AEAD；密钥派生使用经过审计的 Argon2id 实现，不使用自制 KDF 或直接 hash 密码。

文件采用二进制 envelope，不以可被编辑器误识别的明文 Markdown 前缀开头：

```text
magic(8) | protocol_version(u16) | flags(u16) | key_slot(u32)
salt(16) | nonce(24) | ciphertext_len(u64) | ciphertext | auth_tag
```

具体字节序、magic、协议版本和 flags 值必须在实现计划中固定并写入测试向量。AEAD 的 associated data 至少绑定 magic、协议版本、flags、key slot、salt、nonce 和密文长度。未知版本、非法长度、截断、尾随字节、错误 key slot、认证失败和解码失败必须分别映射为稳定错误分类，不得尝试宽松解析。

密文载荷使用版本化序列化结构，至少包含文档类型、正文、标题投影所需的换行信息和必要的保存元数据。载荷不重复保存可由正文计算出的索引字段。所有明文元数据都必须经过下节的逐项批准；默认策略是敏感字段全部进入密文。

## 4. 密钥与解锁生命周期

- 每个加密笔记使用随机数据密钥；数据密钥由用户密钥加密或封装，`key_slot` 标识密钥服务中的版本，不把原始密钥写入 catalog 或文件名。
- 用户主密钥来自操作系统安全存储；密码口令只用于解锁安全存储或派生临时密钥，不能作为文件密钥直接使用。
- 应用启动时不自动解锁；打开加密笔记时进入独立的 locked/unlocked 状态，未解锁只能读取非敏感状态和执行解锁操作。
- 解锁密钥只在内存中存在于最小生命周期；关闭笔记、切换工作区、锁定应用或显式退出时清除会话密钥，并取消尚未完成的明文保存任务。
- “忘记密钥”只清理本机安全存储中的密钥引用并提示用户恢复备份；不得删除密文或伪造新的空密钥。
- 密钥不可用、用户取消、认证失败和安全存储故障必须区分，均不得回退到明文读取。

## 5. 明文与密文元数据

首版默认将标题、标签、目录相对路径、创建时间、修改时间、摘要、正文、文档类型和原始换行信息全部放入密文。catalog 只保留随机 `NoteId`、生命周期、加密协议版本、key slot、文件大小、密文 content hash 和必要的排序时间；这些字段不能用于恢复正文语义。

FTS 不为加密笔记建立明文索引。搜索加密笔记时只能在已解锁会话的内存索引中工作，关闭或锁定时销毁；若首版不实现内存搜索，则明确不支持搜索，而不是把标题或正文写入 SQLite。

文件路径使用随机稳定文件名或不含语义的 NoteId 编码。回收站路径、冲突副本和 catalog backup 同样不得泄漏标题、标签或正文。

## 6. 创建、加载、保存与冲突

### 创建

创建请求只有在密钥服务可用并成功生成、封装和持久化数据密钥后才允许创建 catalog 记录和加密文件。任何一步失败都必须清理临时密文和未完成的 catalog 事务，不能留下明文文件、半成品密文或标记为加密但不可加载的记录。

### 加载

先读取并严格验证 envelope，再通过 key slot 获取密钥，最后验证 AEAD 并解码载荷。认证失败或协议错误时保留原文件不动，返回可辨识错误；不得把错误内容当作空文档打开并允许保存。

### 自动保存

保存采用同目录临时文件、flush/sync、原子替换的顺序。旧密文在新文件完成认证写入和同步前保持可读。临时文件继承严格权限，失败后尽力清理但不删除旧文件。dirty snapshot 和 autosave 请求只携带受保护的会话数据或加密后的快照句柄。

### 外部修改与冲突副本

通过密文 content hash、文件大小和修改时间检测外部变化。无法解密外部版本时不得覆盖；冲突副本继续使用加密 envelope，不能把两个版本导出为明文临时文件。冲突解决必须在已解锁会话中生成新的认证密文。

### 回收站与恢复

回收站移动只改变不泄漏语义的路径和 catalog 生命周期；文件内容保持同一加密协议。恢复与普通移动一样使用“不覆盖目标”策略，NoteId、数据密钥和协议版本保持稳定。

### 备份与崩溃

catalog backup、替换前副本和崩溃恢复文件只能包含 catalog 的受限字段和加密 envelope。启动清理只能删除已确认完成或明确过期的临时文件；无法判断归属时保留并报告诊断，不做盲删。

## 7. 错误分类与安全日志

加密引擎至少提供：`UnsupportedVersion`、`MalformedEnvelope`、`AuthenticationFailed`、`KeyUnavailable`、`UnlockCancelled`、`DecodeFailed`、`AtomicWriteFailed`、`ExternalConflict` 和 `SecureStorageFailed`。面向用户的错误可以本地化，但内部错误不得包含正文、标题、标签、口令、密钥、nonce 或完整密文。

测试日志使用固定占位符。生产日志只允许记录 NoteId、协议版本、错误分类和操作阶段。

## 8. 测试向量与验收门槛

加密引擎计划必须提供固定测试向量，覆盖：

- 已知密钥、salt、nonce、associated data 和明文到 envelope 的确定性结果；
- 单字节密文、tag、header、长度和版本篡改均被拒绝；
- 截断、尾随字节、未知 flags、错误 key slot 和非法长度均被拒绝；
- 正文包含中文、emoji、NUL、CRLF、空文档和大文档时可往返；
- 创建、自动保存、断电替换、外部冲突、回收站恢复和 catalog backup 的故障恢复；
- 锁定后内存搜索、快照、日志和临时文件不残留明文；
- 密钥不可用、用户取消和忘记密钥不会改变旧密文或 catalog 状态。

安全评审通过前，编辑区只实现普通笔记路径和只读“未加密”展示；不得加入“加密笔记”创建选项。评审通过后，必须为加密引擎单独生成细化执行计划，再由编辑区计划接入。
