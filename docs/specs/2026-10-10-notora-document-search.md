# Notora 文内搜索设计

## 现状与目标

Notora 的 `Cmd/Ctrl+F` 当前固定聚焦左侧笔记库搜索。共享层已有文档级
`SearchState`、搜索栏组件及插件搜索高亮，但 Notora 未组装文内搜索入口、
输入路由和结果导航。本次补齐当前文档查找，不扩展为查找替换。

## 推荐交互

- 有已加载且可见的文档时，`Cmd/Ctrl+F` 打开编辑区顶部的文内搜索栏，聚焦并选中查询。
- 无可搜索文档时，`Cmd/Ctrl+F` 保留聚焦笔记库搜索的行为。
- `Cmd/Ctrl+Shift+F` 始终聚焦笔记库搜索；两类搜索各自保存输入。
- 编辑器工具栏增加“文内查找”入口，提高可发现性。
- 选中的单行文本可填入查询；否则保留当前文档上次的查询。
- 输入后更新匹配数量和正文高亮，显示当前序号与总数，并滚动定位当前匹配。
- `Enter` / `Shift+Enter` 和上一处、下一处按钮循环导航。
- `Esc` 或关闭按钮关闭搜索栏，清理搜索输入法组合状态，将焦点交还正文。
- 中文输入法的预编辑只显示在搜索输入框，提交后才更新查询，不能修改正文。
- 空查询不高亮，无结果显示明确的零匹配状态。
- Markdown 编辑模式与源码模式、纯文本、外部文档、回收站只读文档均可查找。
  思维导图先通过现有源码切换入口使用文内查找，避免引入节点搜索的新协议。
- 切换文档时查询和当前匹配归属于各文档，焦点不得遗留到不可见输入框。
- 首期采用普通文本匹配，不暴露尚未接通的替换操作。

## 架构边界

按三项子任务实施，每项修改范围尽量限制在三个文件以内：

1. 文档搜索控制：使用共享文档状态与搜索引擎，封装查询更新、结果导航和编辑后重算。
2. 搜索栏组合：应用层映射纯数据输入，UI 组件不依赖 Notora 状态；搜索栏占用编辑区高度，
   同步正文视口、滚动条、命中测试和输入法候选窗口坐标。
3. 入口与输入路由：接通快捷键及工具栏，明确搜索输入、正文、笔记库输入的焦点归属。

现有工作区的 Markdown builder/view 和 Notora runtime 未提交改动予以保留，
实施时避免覆盖，必要的接入点采用最小变更。

## 验证

先添加失败测试，覆盖快捷键打开当前文档搜索、输入不落入正文、中文匹配计数、
循环导航、关闭后回到编辑器、文档切换、只读查找及笔记库快捷键。
验证 Markdown 源码偏移与可见高亮/滚动定位一致，正文修改后不能使用旧匹配范围。
运行相关模块测试与编译检查，完成后执行 `./scripts/verify.sh`；对既有改动导致的
失败单独说明。若可运行图形界面，再检查搜索栏布局及中文输入法实际交互。

## 备选方案

- 仅新增快捷键：改动小，但搜索入口仍难发现，不能完整改善体验。
- 推荐的完整文内查找：覆盖打开、输入、高亮、计数、导航和焦点闭环。
- 同时加入替换和正则：范围更大，涉及编辑事务与只读权限，留待独立需求。

本方案已于 2026-10-10 获用户确认。实现包含纯文本及 Markdown 的文内查找，
查询保存在各文档的 SearchState 中。搜索覆盖色限制透明度，保证正文可读；
编辑器弹出菜单优先处理输入，并绘制在搜索栏上方。
