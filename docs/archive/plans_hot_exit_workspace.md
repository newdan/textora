# 全局工作区与 Hot Exit (热退出) 实施计划

## 1. 目标与背景
利用全局 YAML/JSON 存储，实现无缝“热退出”(Hot Exit) 功能与“临时工作区”机制，彻底消除应用退出时的打断感。

核心交互规则：
1. **启动与空态**：自动创建未命名空文件（Untitled）。输入内容即变更为“未保存”。
2. **打开新文件**：若当前仅有一个空文件，则被静默替换；否则新建标签页。
3. **关闭标签页 (Close Tab)**：主动关闭操作。空文件直接关闭；有修改的文件（真实或临时）弹出传统保存提示（保存/不保存/取消）。
4. **退出程序 (Quit App)**：隐式操作，无弹窗。将所有状态静默序列化到本地全局缓存（YAML/JSON）。
5. **恢复启动 (Restore)**：读取全局缓存，1:1 恢复上次退出时的所有标签页和未保存内容。

---

## 2. 详细开发阶段拆分 (Phases)

按照“原子化、独立、不互相影响”的原则，我们将整体改动拆分为以下 5 个严格独立实施的阶段。

### Phase 1: 基础状态模型与全局序列化 (底层基建)
*   **目的**: 建立内存数据与本地全局缓存的转换能力，为退出恢复提供数据基石。
*   **重点**: 定义统一的工作区数据协议；使用 YAML（或轻量级 JSON）作为全局存储格式，存储位置类似 `~/.config/[App]/workspace.yaml`。
*   **边界**:
    *   硬盘空间不足导致的写入失败（需要错误降级）。
    *   序列化时特殊字符（如二进制数据错误混入文本）导致的格式损坏。
*   **性能门槛**: 文件落盘总耗时必须严格控制在 `< 50ms` 内，以避免在后续阶段拦截退出时造成应用卡死假象。
*   **具体改动**:
    *   `[NEW]` `WorkspaceState` 模型：包含 `version`, `lastUpdated`, 及其挂载的 `Tab[]` 数组 (`id`, `filePath`, `content`, `isDirty`, `cursorPosition`)。
    *   `[NEW]` `StorageManager` 模块：负责跨平台寻找系统全局配置路径，并提供 `WriteConfig(state)` 与 `ReadConfig()`。
*   **验证方案**:
    *   *自动化测试*：构造包含 5 个虚拟 Tab (部分带特殊字符、部分带超大文本内容) 的模型对象，执行序列化并写入磁盘，随后反序列化读取并使用断言验证对象树 100% 相等。

### Phase 2: App Quit 事件拦截与静默保存 (控制流)
*   **目的**: 彻底移除退出时的“是否保存”弹窗，实现真正的零感知热退出。
*   **重点**: 准确接管操作系统级别的 `Quit` 或主窗口的 `Close` 信号，截断原有的生命周期。
*   **边界**:
    *   系统强制杀进程 (如 `kill -9`) 无法被拦截，这部分属于系统极限，合理忽略。
    *   如果缓存写入发生错误卡死，会导致应用迟迟不退出。
*   **性能门槛**: 整个 Quit 事件处理（触发保存到彻底释放资源）流程耗时不得超过 `200ms`。
*   **具体改动**:
    *   `[MODIFY]` 主控 App 的退出事件回调：完全删除旧版 `CheckAllDirtyTabsForPrompt()` 的检测与 UI 阻塞逻辑。
    *   `[MODIFY]` 替换为：在退出回调的最开头，同步调用 `StorageManager.WriteConfig()` 保存当前快照，随后调用原生 `ForceExit()` 终止进程。
*   **验证方案**:
    *   *手动集成测试*：运行应用，敲击几行不规则代码制造“未保存”状态，不保存，直接按下 `Cmd+Q` (Mac) 或点击红叉。验证：(1) 应用立刻关闭且绝对不弹窗 (2) 检查 `~/.config/.../workspace.yaml` 是否成功更新时间戳且包含刚才的输入。

### Phase 3: 启动恢复机制与空态处理 (生命周期)
*   **目的**: 完美重现用户上次离开时的现场，做到“无缝衔接”并优化多余的空标签体验。
*   **重点**: 在启动初始化流程中尽早加载并应用缓存配置；实现空文件静默替换法则。
*   **边界**:
    *   缓存的 YAML 语法被外部手动损坏，解析失败。
    *   YAML 记录的真实文件路径 (如 `/tmp/test.go`) 在应用关闭期间被外部系统删除了，此时读取必定失败。
*   **性能门槛**: 相比于直接打开空程序，解析 YAML 并重绘旧状态增加的启动时间应 `< 100ms`，保障核心“秒开”优势。
*   **具体改动**:
    *   `[MODIFY]` 启动初始化函数 (`AppInit`)：检测缓存是否存在且合法。如果合法，利用 YAML 数组批量实例化 Tabs 并填充缓冲内容，复原光标和滚动条坐标。
    *   `[MODIFY]` 外部事件（如拖拽文件、双击打开）：加入状态机判断，若当前判断为“唯一标签页且为空未修改”，直接在原 Tab 句柄上挂载新文件，而不触发 `CreateNewTab`。
*   **验证方案**:
    *   *鲁棒性验证*：手动修改 YAML 文件注入非法语法，启动应用，断言应用不会崩溃，而是输出警告并回退到干净的空文件状态。
    *   *外部删除验证*：恢复一个在外部被删除的实体文件，断言应用能将其转为“有内容但路径不存在的未保存临时文件”或给出合理降级，不造成闪退。
    *   *全链路验证*：重复“编辑->退出->打开”流程，校验光标位置、Dirty 标识 (小圆点) 和纯临时文件标题是否完全一致。

### Phase 4: Tab Close 事件的安全拦截 (UI/交互)
*   **目的**: 保护用户主动表达“丢弃/处理文件”的意愿，防止手滑误删重要的工作成果。
*   **重点**: 细致区分文件底层类型，精准控制传统弹窗的触发时机。
*   **边界**:
    *   用户高频连按关闭按钮可能导致重复挂载多个弹窗。
    *   用户在系统弹框中点击取消时，必须保证内存数据和 UI 状态毫不受损（回滚安全）。
*   **性能门槛**: 弹窗和计算逻辑响应要求 `< 16ms`，确保无卡顿感。
*   **具体改动**:
    *   `[MODIFY]` `OnTabCloseButtonClicked` 处理器，引入判断树：
        1. 仅存在空内容且未被修改：直接销毁。
        2. 是临时文件 (`filePath == null`) 且有输入：弹窗“保存/不保存/取消”。选保存调出操作系统的 `SaveAs` (另存为) 弹框落地。
        3. 是真实文件且被修改：同样弹窗。选保存直接调用 `WriteFile`。
*   **验证方案**:
    *   *全场景手工测试*：同时创建纯空 Tab、带有乱码内容的草稿 Tab、修改过行号的实体文件 Tab。依次点击它们的 `X` 按钮，严格观察逻辑分支是否进入正确的作用域（该弹的弹，该直接消失的消失），并走通另存为的全流程。

### Phase 5: 临时文件智能命名与草稿箱 (体验进阶)
*   **目的**: 消除满屏 `Untitled-x` 带来的视觉污染，大幅降低用户同时管理多个草稿时的心智负担。
*   **重点**: 监听文本输入变化事件，利用防抖（Debounce）处理提取首行内容的逻辑，动态更新 Tab UI。
*   **边界**:
    *   用户反复删除首行导致的频繁 UI 闪烁。
    *   首行全是不可见字符（空格/回车）或超长字符串的截断问题。
*   **性能门槛**: 事件提取与字符串截断耗时 `< 2ms`，且必须防抖执行（例如延迟 300ms），绝不允许拖慢主线程用户的打字刷新率。
*   **具体改动**:
    *   `[MODIFY]` 编辑器的 `OnChange` 事件处理器中注入 Debounce 包装的回调。
    *   `[NEW]` `ExtractTitleFromContent(content)` 工具函数：提取非空的第一行，过滤特殊字符并截断至最多 20 个字符。
    *   `[MODIFY]` 调用 `Tab.SetTitle()` 通知 UI 层重绘标签页文字。
*   **验证方案**:
    *   *交互测试*：快速键入大段文字并包含换行，观察 Tab 标题是否在停止输入后优雅地变成第一行的截断内容；删除全部文字后，标题退化回默认的“未命名”。
